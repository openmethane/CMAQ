# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Open Methane's fork of US EPA CMAQ 5.0.2 (Fortran/C, csh build scripts). The main science change is the `CH4only` chemical mechanism (`models/CCTM/MECHS/CH4only`) plus matching profiles in `models/BCON/prof_data/CH4only` and `models/ICON/prof_data/CH4only`. Other fork changes are bug fixes, WRFv4 support, and build changes so everything compiles and is packaged in Docker. It is published as two Debian packages on GitHub releases, `openmethane-cmaq` (MCIP, ICON, BCON) and `openmethane-cmaq-dev` (the build environment CMAQ-Adjoint builds against: libraries, `bldmake` and `config.cmaq` under `/opt/lib` and `/opt/scripts`). No image is published; the last one was `ghcr.io/openmethane/cmaq:1.0.2`. See `README.md`, `docs/building.md` and `docs/development.md`.

Most of `models/` and `tools/` is untouched upstream EPA code. Fork-specific work lives mainly in `Dockerfile`, `scripts/` (build/config scripts), `tests/`, and the `CH4only` mechanism/profile directories.

## Build and test

The supported build is the Dockerfile. A native build isn't supported, but `docs/building.md` documents it and the `native-build.yaml` workflow follows that document literally, so keep the two in step (the commands in `<!-- ci:run -->` blocks are what CI runs).

```bash
make build   # docker build --target debs: both .deb files into dist/
make test    # --target test: installs openmethane-cmaq in a clean debian:trixie-slim, runs tests/check-libs.sh and tests/test-all.sh
```

There are no unit tests. `tests/test-all.sh` runs MCIP → ICON → BCON in sequence (each later step consumes MCIP output) against the small WRF fixture in `tests/test-data/wrf`, and only checks that each output file exists and is non-empty. `tests/check-libs.sh` runs `ldd` over every ELF file in the installed package. To run one step, run a container from the `test` stage interactively, copy `tests/test-data/*` into a dir, export `M3DATA` to it, and run `tests/test.run.mcip` (ICON/BCON need MCIP's `GRIDDESC` and `METCRO3D` output first).

## Build architecture

The `Dockerfile` is the source of truth for what gets built and in what order, and `scripts/build.sh <step>` (which only dispatches to one script per step) runs each step in the Dockerfile, CI and a native build. Only these are compiled (executables under `/opt/cmaq/bin`, libs under `/opt/lib`):

1. `ioapi`: I/O API 3.1, downloaded from cmascenter.org, checked against a recorded SHA-256, and built with the Makefile/Makeinclude overrides in `scripts/ioapi/`.
2. `pario` and `stenex`: `models/PARIO` and `models/STENEX` via their `makefile.gcc`.
3. `bldmake` (`models/BLDMAKE`, via `scripts/build/bldit.bldmake`), the CMAQ tool that generates Makefiles from `cfg.*` files.
4. `bcon` and `icon` via `scripts/{bcon,icon}/bldit.*` (these use bldmake). They default to `MECH=CH4only` and pull mechanism files from `models/CCTM/MECHS/$MECH` and profiles from `models/{BCON,ICON}/prof_data/$MECH`.
5. `mcip` via `scripts/mcip/build_mcip.sh` (plain `make` in `scripts/mcip/src`).

CCTM and its variants (`CCTM_APT`, `CCTM_DDM3D`, `CCTM_ISAM`, `CCTM_STM`, `CCTM_VBS`), JPROC, PROCAN and `tools/` are **not** built. `models/CCTM` is copied in only for its `ICL` and `MECHS` directories.

All csh build scripts `source ../config.cmaq` (`scripts/config.cmaq`, shipped in `openmethane-cmaq-dev` at `/opt/scripts/config.cmaq`). It sets compilers (`mpif90`/`mpicc`), gfortran flags, and library paths (`IOAPI_*`, `NETCDF_*` via `nf-config`, `PARIO_LIB`, `STENEX_*`). The `EXEC_ID` (`Linux_<arch>gfort`) must match the I/O API build dir naming in `build_ioapi.sh`. Compiler-flag changes usually need to go here and/or in `scripts/ioapi/Makeinclude.*`. The trixie base image ships GCC 14, which turns several legacy C diagnostics into errors; the I/O API build downgrades them rather than patching vendored sources.

The Dockerfile stages are `toolchain` → `libs` → `package-dev` (makes `openmethane-cmaq-dev`) → `build` (a clean trixie with only that package installed, which builds MCIP/ICON/BCON, so every build proves the `-dev` package is enough on its own) → `package` (makes `openmethane-cmaq`) → `debs` (`FROM scratch`, both `.deb` files) and `test` (a clean trixie with `openmethane-cmaq` installed). A package is a snapshot of files at the paths the build put them: don't move, rename or rewrite anything in `scripts/build-deb.sh`. `Depends:` for `openmethane-cmaq` is generated by `dpkg-shlibdeps`, so a new shared-library dependency needs no list edit; the `-dev` package's `Depends:` is the toolchain, listed in the Dockerfile. A new file the runtime needs (such as the ICON/BCON profile `.dat` files) must be added to the `package` stage's file list.

## Releases, versioning, changelog

- The version lives in `pyproject.toml` (the Python project exists only to drive `uv version` and `towncrier`; there's no Python code). Don't bump it by hand. The `Create release` GitHub workflow bumps it, builds `CHANGELOG.md` with towncrier, tags `vX.Y.Z`, then bumps to the next `.devN` pre-release.
- The package version is the pyproject version converted to a Debian version by `scripts/debian-version.sh` (`1.1.1.dev1` → `1.1.1~dev1`) and passed as the `DEB_VERSION` build arg; local builds get the pyproject version. `release.yaml` builds both packages from the tag via `build-packages.yaml` (which tests them), checks their versions, and attaches them and `SHA256SUMS` to the GitHub release. PR CI (`build.yaml`) runs the same build and uploads the `debs` artifact. `dev-build.yaml` (by hand) publishes a `dev-pr<PR>-<sha7>` pre-release that `dev-cleanup.yaml` deletes when the PR closes. Nothing is pushed to ghcr.
- A PR that changes what gets released (the image, its build or its outputs) needs a towncrier fragment in `changelog/` named `<PR number>.<type>.md`, where type is one of `breaking`, `deprecation`, `feature`, `improvement`, `fix`, `docs`, `trivial`. Write it for users, in the past tense, as a single paragraph. Never edit `CHANGELOG.md` directly for new entries. Preview with `uvx towncrier build --draft`. PRs that don't change the release, such as agent instructions, contributor docs or PR templates, get no fragment and leave the template's changelog checkbox unticked.
- PR descriptions follow `.github/pull_request_template.md`. The first line says whether the PR needs human review (`**Review:** needed — <reason>` or `**Review:** not needed — <reason>; merging <when> unless someone objects`). Decide using "Code review" in `docs/development.md`: anything that can change science outputs (running source, the `CH4only` mechanism or profiles, compilers, flags, library versions, base image) needs review.

## Before opening a pull request

For any change that isn't mechanical (see "Code review" in
`docs/development.md`), review it from a fresh context before opening the pull
request, and again after reworking it substantially. Skip this for formatter
runs, dependency bumps and CI-only changes, or if the operator asks you to.

Launch the `reviewer` subagent (`.claude/agents/reviewer.md`). Give it:

- the goal of the change and the diff range (e.g. `main...HEAD`)
- the numbers of any issues the change addresses
- any constraints the operator set during the task, such as an approach to use
  or avoid, or something to leave unchanged

Don't give it your reasoning or your view of whether the change is correct,
because it will tend to confirm what it's told.

Independent reviews of the same change find different problems. When a change
both can alter model outputs or break the CMAQ-Adjoint build, and touches the
build (compilers, flags, base image, libraries), the mechanism, or several
components, offer the operator a second review, run in parallel with the same
brief. Each review costs tens of thousands of tokens, so run the second only
if the operator agrees. Merge the two reports, counting a finding both raised
once, before dealing with them.

Deal with each item it reports:

- **Wrong, with a clear fix:** fix it, if the fix stays within the scope of the
  task and doesn't go against the operator's instructions or the project's
  guidance.
- **Needs the operator's decision:** ask the operator, with the options and
  your recommendation. This includes items with an obvious fix that would
  change science outputs or methodology, widen the change beyond what was
  asked, or make the pull request need human review when it otherwise
  wouldn't.
- **Not a problem:** dismiss it, but list it in one line to the operator with
  your reason, because you're judging criticism of your own work.

This review is part of preparing the change. Don't mention it or its findings
in the pull request description or comments.
